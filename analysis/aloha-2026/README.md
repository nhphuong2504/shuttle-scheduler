# Aloha 2026 — in-progress tournament dataset

A point-in-time snapshot of a live two-day tournament, exported so the scheduler's output and the
live reflow can be analysed without a database. Unlike `../viet-nam-open-2026`, this tournament is
**not finished**: four matches were on court when the desk stopped and five finals were never
started.

## Reproducing

```sh
npm run analysis:aloha                 # export -> metrics -> charts, in that order
# or, one step at a time:
node analysis/aloha-2026/export.mjs     # Supabase Management API, SUPABASE_ACCESS_TOKEN from .env
node analysis/aloha-2026/analyze.mjs
node analysis/aloha-2026/charts.mjs
```

`export.mjs` is read-only and never writes to Supabase. Player email, phone and profile id,
organiser contact fields and the owner profile id are dropped on the way out. The token is never
printed or written to a file.

## Time semantics — read this before analysing

Every timestamp is UTC; the app renders `America/Chicago`. Day 1 ran 12:30–17:00 local, day 2
09:30–20:30 local. Day 1 actually used 8 courts (courts 9–10 existed and were in earlier builds but
were dropped from the last pre-play plan; court 11 was created during day 2). Day 2 used all 11.

- **`scheduled_time`** is the *last* published time. It is rewritten by the live reflow, so it is
  almost always within a minute of `started_at`; comparing the two measures nothing.
- **`started_at` / `ended_at`** are what actually happened.
- **`first_published_time`** (in the CSVs) is the earliest time the activity trail ever held for the
  match. For 85 placement matches this is the 12:15 build that anchored at **00:15 local**, outside
  the day window; those values make `drift_from_first_publish_min` read about 12 hours and are a
  build artefact, not live reflow.

The report therefore uses three derived measures that are not in `matches.csv`:

| Measure                 | Definition                                                                                     |
| ----------------------- | ---------------------------------------------------------------------------------------------- |
| live time shifts        | `time-shifted` rows after the first match started, per match; the reflow's churn               |
| notice                  | `started_at −` the moment the played time was published (median 0.3 min: the reflow announces) |
| plan at an instant      | `scheduled_time` replayed from `desk_activity` (`court-moved`, `time-shifted`, `reset`)          |

`analyze.mjs` replays those three actions into a timetable snapshot and checks it for court
overlaps, player overlaps, rest-gap violations and knockout dependency violations. All four
snapshots (day 1 12:29, day 1 13:29, day 2 09:55, day 2 13:00) are clean.

## Caveats

- Four matches were in progress at export and five finals were never started, so day-2 tail
  metrics and the 12/20 champion count describe a truncated tournament.
- `tournament_day_courts` was written on 2026-10-27 16:03 local, after day 1 had been played. Only
  day 1 has rows (9 courts). The intended court set at planning time is therefore unknown.
- The day-2 window was created at 12:25 on day 1, 10 minutes before play started; the first build at
  12:15 had no day-2 window at all.
- The first build placed 85 matches at 00:15–01:35 local, then was rebuilt four times between 12:23
  and 12:27. The final pre-play plan is the 12:27 one.
- The tournament is staging data. Player identities are synthetic, but the schedule, the durations
  and the audit trail are real output of the product.
