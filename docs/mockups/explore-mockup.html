The trip the visitor takes
1 · Explore — the card offers the door, not a form Sign in to register /auth?redirect=%2Ftournaments%2F<id>&intent=register
2 · Sign in — the page says where this ends You'll go straight to that tournament's registration form.
3 · The form — where it was always going /tournaments/<id> — the Register panel, already open for this caller
Shipped, and why the message is not "sign in to continue". The sign-in page's own heading already says Sign in to Tournova, and its copy names the two doors — so repeating "sign in or create an account" on the notice would be the page telling somebody what they are looking at. What a visitor cannot know is what happens next: whether signing in loses the thing they clicked. So the notice carries the destination and nothing else. It is drawn only beside a return address, and intent is a closed vocabulary (register) rather than free text, because this value selects copy that a trusted page prints.

09

Narrow viewport — 390px

The layout the phone gets: one column of cards, filters stacked, the chip row left-aligned. The card’s min-w-0 plus break-words is what stops a long venue or a two-day range scrolling the page sideways — the defect that made /explore overflow by 29px at 320px.

Mockup caveat: the chips and type inside this frame are drawn one step smaller than the real page so the 390px layout fits in the screenshot. The shipped control is min-h-11 (44px) at every width — see § 04 for the real sizes.

Card anatomy

The decisions the shipped card encodes, so a redesign can keep or deliberately drop each one.

  • In progress Open

    KL Open 2026

    • Sep 19, 8:00 AM GMT+8 → 6:30 PM GMT+8
    • Stadium Badminton Kuala Lumpur
    • 128 entries · 6 events
    Follow live scores Register
    • pills row · topLifecycle first, window second, and only when the window adds a fact. Two pills maximum, so the row never wraps to two lines at desktop width.
    • h3 · 24px displayLarger than TournamentCard's 14px — this card is a thing to choose between, that one is a row in a work list. The name is the anchor, not the card: a card-sized click target swallows the footer buttons on touch.
    • facts · 16px, when/where/how bigRange, then venue, then counts — the order a visitor asks them. TournamentCard puts the venue first instead, and it is the only difference between the two facts lists.
    • facts · min-w-0 + break-wordsStructural, not cosmetic. truncate would contribute the whole nowrap string to the grid item's min-content width and scroll the page sideways.
    • action · one primary by stateIn progress → Follow live scores filled; Completed → See results outlined; Upcoming → View details outlined. A filled button for every state would make every card equally loud.
    • Register · additive, window-gatedDrawn only when registration_state === "open", beside the state action. Both are filled when they co-render, which is the one place two primaries stand next to each other.
    • Register · two readings, one controlSigned in → Register, to the participant page. Visitor → Sign in to register, to /auth carrying the participant page as the return address and intent=register as the errand. Same treatment, same word the participant page itself uses, so the gate reads as the same offer behind a door rather than as a different one.
    • card · h-full, mt-auto footerCards in a row share a height via the grid, and the footer pins to the bottom, so the buttons line up across a row of cards with different name lengths.

    Directions, if you want to move it

    Sketches only — no tokens, no final copy. Three shapes for the same job, with what each one costs.

    A · Keep it, tighten the card

    Same page. Smaller title, facts on one line with a separator, one action instead of two.

    + Cheapest change; the page already works.

    − Still two columns of tall cards; a long list needs a lot of scrolling.

    B · Live first, list after

    One wide banner card for the in-progress tournament, the rest as compact rows.

    + Answers “what is on right now” before anything else; scales to many tournaments.

    − New component, and the compact row loses the venue detail.

    C · Filters as a rail

    Status and event-type facets down the left, a wider result column on the right.

    + Room for more facets (event, date, region) without crowding the top.

    − The rail eats width on a laptop; needs a drawer below lg.

    12

    Findings while reading the code

    Things the mockup made visible. None of these are visual, all of them are in the files you are editing.

    1 · Register pointed at an address the IA doc called unlinked — fixed It linked to /tournaments/$tournamentId, which information-architecture.md §2 recorded as “currently unlinked … registration is out of the read-only experience while it is redesigned”. Registration now has a real gate: a signed-in caller goes to that page and registers; a visitor is sent to sign in carrying it as the return address and the word register as the errand, so the sign-in page can say where this ends. The IA doc, routes.ts and the participant page's own comment were updated with it. See § 03.
    2 · TournamentCard imports formatters it does not use It imports countText and dateRangeText from summary-format.ts, then defines local count() and dateRange() and calls those instead. The local pair is a near-copy of the shared pair — same branches, same Intl options, same output — which is exactly the duplication that file’s own docblock says it exists to prevent: “the three formatters live here rather than in either surface, and both import them”. Nothing is broken today and noUnusedLocals is false in tsconfig.json, so typecheck passes; the risk is the two drifting the next time one of them is touched.
    3 · The facts order differs between the two cards ExploreCard reads when → where → how big. TournamentCard reads where → when → how big. Both are deliberate per their comments, but they do mean the same tournament describes itself in two orders depending on the page. Cheap to unify, or worth documenting as intentional.
    4 · The chip row has no pressed state beyond colour aria-pressed is correct and the fill carries it, but “Any status” pressed and “Upcoming” pressed are the same shape in the same colour — a reader scanning quickly sees a filled chip, not which filter is on. The label is the redundant channel, which is consistent with the rest of the system; flagging it only because a filter row is where it is most load-bearing.
